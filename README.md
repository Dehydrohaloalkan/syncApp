# SyncApp — личная машина → GitHub → рабочая машина

Приложение устанавливается на двух машинах. На личной вы пишете код и создаёте
Git-коммиты. SyncApp подписывает и шифрует изменения каждого коммита и публикует
пакеты в отдельной GitHub-репе `junk`. На рабочей приложение получает junk,
проверяет подпись, расшифровывает пакеты и применяет выбранные изменения к
индексу и файлам рабочей репы. Рабочий коммит вы создаёте самостоятельно.

Рабочая сторона только читает GitHub: транспортные commit/push, обратная
передача и отправка квитанций отсутствуют. Decimen, QR и камера исключены.
Начальную личную копию кода вы готовите отдельно. Получение пакетов запускается
кнопкой синхронизации; фонового опроса пока нет.

[План](PLAN.md), [проверки](docs/TESTING.md), [ревью](docs/REVIEW.md).

## Запуск

Для запуска из исходников нужны Git и .NET SDK 10. Ключи X25519, шифрование
и расшифровку выполняет сам SyncApp. Для сборки из чистого клона пакеты NuGet
включены в каталог `third_party/packages`. На обеих машинах заранее
клонируйте отдельную transport-репу junk и настройте upstream ветки.
Личной стороне нужен доступ на публикацию, рабочей достаточно чтения.
Git identity исходных реп настраивается обычными средствами Git.

Из корня SyncApp:

```bash
dotnet build SyncApp.slnx
dotnet run --project SyncApp/SyncApp.csproj --no-build
```

На личной машине host запускается в WSL рядом с Git и проектами, интерфейс
открывается в браузере Windows. Доступ к localhost необходимо проверить в
своей конфигурации WSL. На рабочей Windows:

```powershell
dotnet run --project SyncApp/SyncApp.csproj
```

Откройте `http://127.0.0.1:5055`.

| Переменная | Назначение |
| --- | --- |
| `SYNCAPP_PORT` | Loopback-порт, по умолчанию 5055 |
| `SYNCAPP_DATA_DIR` | Каталог локального состояния; по умолчанию SyncApp в LocalApplicationData |

Исходники, junk и состояние должны быть в отдельных папках. Выбирайте корни
репозиториев; symlink/junction в этих путях отклоняются. Не запускайте несколько
экземпляров с общей папкой состояния: межпроцессная координация не реализована.
Открытые временные данные создаются в приватном scratch под локальным состоянием
независимо от TMPDIR/TEMP/TMP. На Unix используются права 0700/0600, на Windows
защищённый ACL текущего пользователя.

## Подключение

1. Отдельно подготовьте одинаковый начальный код в чистых исходных Git-репах
   на личной и рабочей машинах. Истории и SHA коммитов могут различаться.
2. На личной стороне создайте проект, указав каталог в junk, существующую
   папку исходников и пароль локальных ключей. Название каталога публично;
   выбирайте нейтральное имя.
3. Введите пароль, отметьте отправку в GitHub и нажмите «Синхронизировать junk».
   Пока рабочий ключ не подключён, публикуется только публичный дескриптор.
4. На рабочей стороне подключите чистую исходную ветку к этому каталогу junk.
   Приложение получает дескриптор; перед подключением независимо сверяется
   отпечаток личного устройства.
5. Скопируйте показанные рабочим приложением публичный age recipient и его
   отпечаток на личную машину. Секретный ключ не копируется.
6. На личной стороне в форме подключения рабочего ключа вставьте recipient и
   проверенный отпечаток. Ключ закрепляется; произвольная замена не допускается.
7. Синхронизируйте личную сторону с отправкой. В junk появятся подписанные
   зашифрованные метаданные начальной базы и доступные личные изменения.
8. Синхронизируйте рабочую сторону. Приложение расшифрует метаданные и проверит
   совпадение содержимого исходной базы. При несовпадении применение блокируется. База уже зафиксирована при
   подключении: после исправления начальной копии создайте новый канал и
   подключение, сохранив прежние ключи и состояние.

Личный отпечаток связывает ключ подписи и публичный age-ключ личного устройства;
рабочий отпечаток относится к age recipient. Секретные ключи защищены локальным
паролем. Версия протокола подключения — 3. После обновления продолжают работать
существующие ключи, каналы и пакеты, созданные прежней версией через age.

## Передача изменений

1. Создайте обычные коммиты в подключённой личной ветке.
2. Укажите количество следующих коммитов (0 — все), отметьте отправку и
   синхронизируйте junk. Один исходный коммит становится отдельным `.age`-пакетом.
3. На рабочей стороне синхронизируйте junk и покажите входящие пакеты.
4. Примените следующий пакет. Можно последовательно применить несколько;
   приложение обновляет индекс и файлы, сохраняя HEAD.
5. Создайте один ручной рабочий коммит с накопленным результатом и нажмите
   «Коммит создан». Приложение проверит итоговое дерево и сохранит локальную
   связь входящих изменений с этим коммитом.

Новые личные коммиты можно публиковать без обратного подтверждения. Личное
приложение знает о доставке в junk, но не знает, применены ли изменения на
рабочей машине. Рабочая сторона сохраняет очередь и состояние принятия локально.

Снятая отметка отправки означает локальную подготовку transport-коммита без push.
Указанное количество включает уже подготовленную очередь. Уменьшить его ниже
числа готовых пакетов нельзя; 0 означает всю цепочку. Переписывать исходные
коммиты после подготовки пакетов нельзя.
Если другой автор продвинул удалённую transport-ветку, истории могут разойтись:
автоматическая синхронизация остановится. Не используйте force push; разрешите
расхождение отдельно, сохранив все транспортные объекты.

## Шифрование и восстановление

Исходники, патчи, исходные сообщения/ветки/пути и метаданные базы находятся
внутри подписанных зашифрованных `.age`-объектов. Открытый `project.json`
содержит только протокольные идентификаторы и публичные ключи. GitHub видит
имена/размеры транспортных файлов, время и историю публикаций.

При отказе push приложение не продвигает исходящий курсор; повторите отправку
после устранения причины. Посторонние staged-файлы и неизвестные изменения junk
блокируют автоматическую публикацию. Рабочая сторона не создаёт в junk файлов
или локальных транспортных коммитов.

После прерывания применения введите пароль и нажмите «Восстановить операцию».
Приложение проверит журнал и фактические файлы; при несовпадении сохранит
пользовательские правки и остановится. Повторное подтверждение не создаёт
дубликатов ручных коммитов или локальных связей.

## Ограничения

- Предел зашифрованного объекта — 64 MiB; разбиение пока не реализовано.
- Поддерживаются линейные коммиты. Merge, amend/rebase подготовленной очереди,
  смена поколения канала и автоматическое разрешение расхождения junk требуют
  дальнейшей работы.
- Рабочие собственные исправления не передаются обратно. Если рабочий код
  расходится с ожидаемой базой, следующий патч блокируется.
- Symlink-файлы, submodules, LFS и нестандартные Git-фильтры не поддерживаются.
- Дополнительные ignored/untracked-файлы, каналы и ротация ключей пока не имеют
  полного пользовательского сценария.
- Тесты восстановления моделируют прерывание в контрольных точках, а не потерю
  питания, повреждение диска или конкурентные внешние изменения.
- Пакеты и деревья обрабатываются в памяти; большие проекты требуют измерений.
- Windows 10 и Windows 11 + WSL требуют отдельной платформенной проверки.
- Старый QR-протокол и локальное состояние несовместимы с версией 3. Автоматической
  миграции нет: используйте новый каталог `SYNCAPP_DATA_DIR` и новые каналы,
  сохраняя прежнее состояние и ключи. Не удаляйте исходные рабочие репозитории.

## Самодостаточные сборки

На машине сборки SDK при необходимости скачает среду выполнения целевой платформы.

```bash
dotnet publish SyncApp/SyncApp.csproj -c Release -r win-x64 --self-contained true --source ./third_party/packages --source https://api.nuget.org/v3/index.json -o artifacts/win-x64
dotnet publish SyncApp/SyncApp.csproj -c Release -r linux-x64 --self-contained true --source ./third_party/packages --source https://api.nuget.org/v3/index.json -o artifacts/linux-x64
```

Переносится весь каталог с wwwroot. Запуск: `SyncApp.exe` на Windows или
`./SyncApp` в Linux/WSL. Для готовой сборки на целевой машине достаточно установленного Git. Артефакты прежнего прототипа требуют пересборки.
Сборка win-x64 сама по себе не подтверждает запуск на Windows 10.

## Проверки и разработка

```bash
dotnet build SyncApp.slnx
dotnet run --project tests/SyncApp.Tests.csproj --no-build
python3 tests/http_security.py
```

Тесты используют временные исходные репозитории, два clone junk и локальную
bare-репу. Браузерные команды и фактические результаты:
[docs/TESTING.md](docs/TESTING.md).

Разработка ведётся через кодера и тестера (`gpt-6-luna`) и ревьювера
(`gpt-6.1-sol`). Координатор проверяет и объединяет результаты.
Правила закреплены в [AGENTS.md](AGENTS.md) и навыке
[syncapp-development](/home/alex/.codex/skills/syncapp-development/SKILL.md).

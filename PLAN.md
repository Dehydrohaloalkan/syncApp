# SyncApp: личная машина → GitHub → рабочая машина

Обновлено: 11 октября 2026 года с учётом ограничения: рабочая машина не может
коммитить или отправлять изменения в GitHub. Этот план заменяет смешанный и
двусторонний маршруты предыдущего прототипа.

[Запуск и использование](README.md), [проверки](docs/TESTING.md),
[независимое ревью](docs/REVIEW.md).

## 1. Подтверждённый сценарий

1. SyncApp установлен на личной и рабочей машинах.
2. Начальную копию кода на личной машине пользователь готовит отдельно.
   Приложение не переносит начальный рабочий код.
3. На личной машине пользователь пишет код и создаёт обычные Git-коммиты.
4. SyncApp подписывает и шифрует изменения каждого коммита и публикует их
   в отдельную GitHub-репу `junk`.
5. Рабочее приложение получает junk, проверяет подпись, расшифровывает входящие
   пакеты и применяет выбранные изменения к файлам и индексу рабочей репы.
6. Пользователь создаёт рабочий коммит сам. Несколько личных изменений можно
   объединить одним рабочим ручным коммитом.
7. Рабочая сторона только читает GitHub. Никаких транспортных commit/push,
   исходящих изменений или отправляемых квитанций.
8. Обратной передачи через Decimen/QR нет. Камера, QR-ресурсы и загрузка
   транспортных файлов удаляются из приложения.

Получение запускается кнопкой синхронизации; автоматический фоновый опрос
не входит в текущий этап. Приложение на рабочем устройстве не запускает агентов.
Три агента используются только при разработке самого SyncApp.

Имена и структура исходников сохраняются. Один канал соответствует паре веток;
проекты имеют отдельные каталоги и локальное состояние. Истории Git могут быть
независимыми: приложение сравнивает digest деревьев, а не равенство SHA коммитов.
Windows 10 на рабочем устройстве и Windows 11 + WSL на личном — целевые платформы.

## 2. Подключение и ключи

Публичный ключ рабочей машины разрешено вручную скопировать текстом на личную.
Это отдельная операция подключения, без передачи кода или секретного ключа.

1. Подготовить одинаковый начальный код в чистых Git-репах на двух устройствах.
2. Настроить два clone junk, GitHub-доступ и upstream. Рабочей стороне достаточно
   доступа на чтение; личной нужен доступ на публикацию.
3. Создать личный проект на существующей подготовленной репе. Зафиксировать
   локальную ветку, baseline-коммит и digest. Создать защищённые локальные ключи
   и публичный дескриптор подключения.
4. Опубликовать личный публичный дескриптор в junk.
5. На рабочей машине получить дескриптор, подключить чистую рабочую ветку и
   сверить отпечаток личного устройства независимым доверенным способом.
6. Создать рабочий ключ локально; показать его публичные данные для копирования.
   В рабочем clone junk при этом ничего не создаётся и не коммитится.
7. На личной машине вставить проверенные публичные данные рабочего устройства.
   Закрепить получателя шифрования; дальнейшая подмена ключа запрещена.
8. Личная сторона публикует подписанные зашифрованные метаданные исходной базы.
   Рабочая сторона расшифровывает их и сверяет digest своей исходной базы.
   Несовпадение останавливает приём. База фиксируется при регистрации; после
   исправления начальной копии нужен новый канал/подключение, а не изменение
   уже закреплённого baseline.

Обе стороны создают ключи и обрабатывают пакеты age v1 внутри приложения.
Формат ключей и протокол v3 совместимы с ранее выпущенными версиями.
Секретные ключи и пароль остаются локально. Рабочая машина расшифровывает
пакеты своим ключом и проверяет закреплённый личный ключ подписи.
Смена ключей требует отдельного управляемого переподключения.

## 3. Транспорт и конфиденциальность

Через junk передаются только публичные данные подключения и подписанные
зашифрованные объекты личной стороны:

```text
<neutral-project-folder>/
  project.json
  channels/<channel-id>/
    baseline/<channel-id>.age
    packages/personal-to-work/<change-id>.age
```

Версия протокола — 3; прежние подключения автоматически не мигрируются.
В `project.json` разрешены версия, идентификаторы и публичные ключи. Код,
имена исходных файлов, реальные ветки, SHA и сообщения исходных коммитов,
метаданные базы находятся внутри `.age`.
GitHub видит публичный дескриптор, транспортные имена/размеры/время и историю.
Название каталога junk выбирается пользователем; для конфиденциального проекта
используется нейтральное имя.

Объекты неизменяемы; локальный журнал связывает известные исходящие файлы с
их хешами. Публикуются только файлы конкретных операций. Посторонние staged
и неизвестные локальные изменения блокируют публикацию. `git add .`, force push
и автоматический destructive reset не используются.

Личная синхронизация получает remote fast-forward, готовит выбранный префикс
коммитов и фиксирует транспортные файлы. Push выполняется явным действием.
Курсор исходящих коммитов продвигается только после успешного push. Отказ
push и перезапуск должны допускать идемпотентный повтор без дубликатов.
Подготовка без push означает только локальный транспортный коммит. Число
выбранных коммитов включает ранее подготовленную очередь; уменьшение ниже её
размера или переписывание подготовленных исходных коммитов отклоняется.

Рабочая синхронизация только получает remote fast-forward, проверяет подключение
и показывает входящие. Даже если исходящий флаг передан напрямую в API,
рабочая сторона не должна выполнять transport commit/push.

Предел приложения — 64 MiB для зашифрованного объекта. Это предел SyncApp:
обычный GitHub блокирует файлы больше 100 MiB
([официальная документация](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)).
Разбиение и политика роста transport-истории — последующие этапы.

## 4. Очередь и применение

Каждый личный коммит получает стабильный ChangeId, ссылку на предыдущее
изменение, base/result digest и зашифрованный подписанный патч.
Порядок задаёт цепочка пакетов, а не транспортные Git-коммиты или время файлов.

Личная сторона может публиковать следующие коммиты без обратного подтверждения.
У отправителя есть статус доставки в junk; статус фактического применения на
рабочей машине ему неизвестен. Не обещать интерфейсом удалённое принятие.

На рабочей стороне:

1. Выбрать следующее доступное входящее изменение.
2. Проверить ветку, исходную базу, HEAD, индекс и файлы.
3. Предварительно проверить патч в изолированном индексе и сверить result digest.
4. Сохранить локальную ApplySession с pending-маркером до изменения файлов.
5. Применить к файлам и индексу без создания исходного коммита, затем завершить
   pending-запись. Следующие пакеты допускаются только при
   точном соответствии индекса и файлов ожидаемому результату предыдущего.
6. Пользователь создаёт один обычный ручной коммит поверх исходного HEAD.
7. Действие «Коммит создан» проверяет итоговое дерево и связывает локально
   группу ChangeId с этим ручным коммитом. Квитанция в GitHub не создаётся.

После [A,B,C] → W следующая база определяется результатом C, а не SHA W.
Дубликаты и переставленные пакеты не должны повторно менять файлы.
Посторонние правки, partial staging, смена ветки, amend/rebase и merge-коммиты
блокируют неподдерживаемую операцию с сохранением пользовательского кода.
Рабочие собственные исправления не передаются обратно; расхождение базы требует
явного разрешения пользователем.

## 5. Восстановление и границы

Сохранить долговечный журнал применения до записи пользовательских файлов.
Восстановление сравнивает журнал с фактическими веткой, HEAD, индексом и digest.
Ожидаемый ручной коммит после сбоя завершается без нового целевого коммита и
без дубликата локальной связи. При несовпадении сохранить файлы и маркер.

Начальный импорт архива и сетевые квитанции прежнего прототипа исключены из
актуального маршрута. Приватный scratch остаётся вне junk и исходников;
TMPDIR/TEMP/TMP не определяют место открытого ключа и пробного индекса.

Межпроцессная координация, произвольные аварийные точки, повреждение диска и
конкурентная враждебная замена путей не доказаны локальными тестами.

## 6. Критерии готовности

- [x] Личная публикация подписанных зашифрованных коммитов в junk.
- [x] Рабочая сторона только читает junk; нет исходящих пакетов, квитанций,
      транспортных commit/push даже при прямом обращении к API.
- [x] Существующие исходные репы, ручное подключение публичного рабочего ключа
      и проверка одинаковой исходной базы.
- [x] Новые личные коммиты публикуются без обратного подтверждения.
- [x] Нет QR/Decimen, камеры, upload/download transport-маршрутов и ресурсов.
- [x] Сохранены накопление изменений, ручные рабочие коммиты и восстановление.
- [x] Пройдены Core, HTTP, browser и независимое ревью окончательной версии.
- [x] Созданы `AGENTS.md` и навык для кодера, тестера и ревьювера.

## 7. Следующие этапы

1. Разбиение больших зашифрованных объектов и ограничение роста истории junk.
2. Координация нескольких экземпляров и более полный журнал публикации.
3. Управляемые новые поколения, ротация ключей, отмена накопленной группы
   с сохранением пользовательских правок.
4. Дополнительные каналы и явно выбранные ignored/untracked-файлы; отдельные
   решения для LFS/submodules и нестандартных Git-фильтров.
5. Проверка Windows 10, Windows 11 + WSL и самодостаточных поставок.

Автоматический опрос GitHub можно добавить отдельным этапом по запросу.

## 8. Три роли разработки

Координатор обновляет план и распределяет непересекающиеся файлы. Кодер
(`gpt-6-luna`) реализует продукт, тестер (`gpt-6-luna`) независимо проверяет
сценарии, ревьювер (`gpt-6.1-sol`) проверяет окончательную версию после исправлений.
